# 风险与生产化关注项

## 证据边界

- **已确认**：当前仓库是 2026-08-26 冻结的“和盛大厦”双端离线交互原型发布包；`README.txt` 明确说明全部数据为演示数据，不提交真实业务系统。
- **已确认**：仓库只有编译产物和本地启停脚本，没有 `src/`、`package.json`、依赖锁、构建配置、测试、CI、环境配置样例或 source map。
- **已确认**：所谓“小程序端”当前是浏览器 React 移动端仿真页（`mini-program/index.html`、`mini-program/assets/index-MfHB7Usc.js`），不是可导入微信开发者工具的原生/uni-app/Taro 工程。
- **已确认**：管理端是原生 DOM 模板字符串 SPA 构建产物（`web-admin/assets/index-Col4iETK.js`），其页面、角色、记录和动作均在浏览器内存中运行。
- **推断**：bundle 可以用于还原页面、字段、状态和流程意图，但不能作为完整需求、可信领域规则或生产代码基线。
- **建议**：PRD 中对每项能力标注“已交互演示 / 仅展示 / 正式版待定义”，避免把点击后 toast 当成已经设计好的业务闭环。

## 风险优先级总览

| 优先级 | 关注项 | 当前证据 | 不先解决的后果 |
|---|---|---|---|
| P0 | 无可维护源码与可复现构建 | 两端仅有压缩 bundle/CSS；无清单、锁文件和 map | 无法安全迭代、升级依赖、定位漏洞或建立 CI |
| P0 | 无 API 与领域契约 | 两个 bundle 无业务 `/api/`、XHR、WebSocket、SSE；`fetch` 仅为 module-preload polyfill | 若依接口与前端字段各自设计，后期大面积返工 |
| P0 | 鉴权、租户隔离和数据权限仅为前端模拟 | `web-admin/assets/index-Col4iETK.js:165` 默认 `roleId: super`，路由与动作权限都在客户端判断 | 越权、跨企业数据泄露、审计失真 |
| P0 | 小程序尚未工程化 | 没有 `app.json`、页面源码、微信登录/订阅消息/支付 SDK | 无法真机联调、提审或验证平台权限 |
| P0 | 文件、支付、消息和第三方系统均未接入 | 上传、导出、复制链接、拨号等多处仅变状态或 toast | 原型“成功”与真实异步失败语义冲突 |
| P0 | 关键业务缺少服务端一致性机制 | ID、本地状态迁移、审批与回写都由前端对象更新完成 | 重复单、丢更新、重复支付/退款、并发审批错乱 |
| P1 | 演示种子存在时间/状态不一致 | 管理端固定 `currentLocalDate: 2026-08-11`，同时含 8 月 12/13 日记录；忽略截止日可早于提交日 | 迁移种子或照抄规则后产生错误 SLA、状态和报表 |
| P1 | UI 成功反馈替代后端回执 | 多个 `show-toast` 声称导出任务已生成、数据已导出或链接已复制 | 用户误以为业务已落库或异步任务已受理 |
| P1 | 静态发布性能未治理 | 资产 22 个、约 11.14 MB；管理端 JS 820,531 B，小程序 JS 347,724 B；大图多为 0.67–1.36 MB | 小程序包体、首屏、弱网和移动流量风险 |
| P1 | 自动化验证完全缺失 | 无单元、组件、契约、E2E、可访问性、视觉回归或安全扫描入口 | 页面多且流程密集，回归成本不可控 |
| P2 | 本地原型服务存在运维脆弱点 | `tools/serve.ps1`、`tools/stop.ps1` 仅面向本机演示 | 不应演化为生产部署方式 |

## 已确认的技术债与功能缺口

### 1. 源码、依赖与可追溯性

- **已确认**：`mini-program/assets/index-MfHB7Usc.js` 只有 9 个物理行、347,724 B；`web-admin/assets/index-Col4iETK.js` 只有 446 行、820,531 B，大段业务代码被压缩在单行内。
- **已确认**：没有 source map，页面/数据/规则与渲染代码混在 bundle；当前只能通过字符串和运行时行为反向梳理。
- **推断**：README 记载的前端冻结点 `0ae90c5` 与 `7e5c3c9` 属于原始工程历史，但当前仓库无法验证这些提交的源文件、依赖版本和测试结果。
- **建议**：在编码前找回两个冻结点对应的原始仓库；若无法找回，则把当前包仅作为验收参考，重新创建管理端与小程序端工程，不要修改压缩 bundle。
- **建议**：建立统一的需求追踪表：原型页面/动作 -> PRD 用例 -> API -> 若依权限标识 -> 数据表/事件 -> 测试用例。

### 2. 原型交互不等于业务闭环

- **已确认**：小程序投诉提交在 `mini-program/assets/index-MfHB7Usc.js:9` 仅打开“投诉已提交”面板，并用 `Date.now()` 截取生成展示工单号；没有请求、重试或真实工单记录追加。
- **已确认**：预约、续租、反馈、订阅开关、上传照片/回单、一键拨打等多项交互只更新 React 内存状态或展示成功态；刷新即恢复。
- **已确认**：小程序账单页明确写着“正式版提供 Excel/PDF 下载”，企业代办页明确写着“正式版可接入在线材料上传”，企业信息变更明确标为演示展示。
- **已确认**：管理端大量导出、新建企业、合同创建、附件预览等动作使用 `show-toast`；例如 `web-admin/assets/index-Col4iETK.js:404-435` 直接提示“任务已创建/已导出/功能为原型演示”。
- **推断**：许多按钮尚未定义失败、重复提交、取消、超时、部分成功、权限变化和异步最终状态。
- **建议**：PRD 为每个写操作补齐前置条件、幂等键、同步回执、异步状态、失败码、重试/撤销、通知和审计要求。

### 3. 状态、时间与数据一致性

- **已确认**：管理端集中状态初值为 `roleId: super`，所有演示集合被编译进 `web-admin/assets/index-Col4iETK.js:1`，动作在 `:165` 附近通过对象复制更新内存记录。
- **已确认**：管理端本地 ID 生成函数按集合现有 ID 的最大尾号加一；这不是并发安全、跨节点安全或可审计的标识生成方式。
- **已确认**：账号/模板状态切换使用可选 `sourceStatus` 与当前内存值比较，属于客户端乐观检查，没有数据库版本号、ETag、事务或锁。
- **已确认**：数据冲突裁决、回写、忽略和小程序配置发布/复核均直接改本地对象；“提交人不能复核”只比较前端传入的 actor/reviewer 字符串。
- **已确认**：演示时钟固定在 `2026-08-11`，但数据中含 `2026-08-12`、`2026-08-13` 的反馈、隐私请求和配置变更；另有忽略记录提交于 8 月 9 日却截止于 8 月 5 日。
- **推断**：SLA、逾期、待裁决、回滚和报表结果会依赖这套固定时钟与不一致种子，不能直接推导生产规则。
- **建议**：若依后端统一提供服务端时间、版本字段、状态机与事务边界；审批/退款/回写/发布使用幂等命令和不可变审计事件。
- **建议**：金额、面积、用量、押金与余额在 PRD 中明确单位、精度、舍入、税率、币种、负数规则和账务不可变性，数据库使用定点数而非前端浮点语义。

### 4. 身份、权限与多租户安全

- **已确认**：当前没有登录 API、JWT、Cookie 会话、微信授权或 token 持久化；刷新后状态恢复。
- **已确认**：页面可见性、角色切换、动作权限和数据范围全在 `web-admin/assets/index-Col4iETK.js` 客户端实现；任何浏览器用户都可修改运行时数据。
- **已确认**：审批/裁决/回写界面允许从演示责任人集合选择 actor，责任人没有绑定可信登录主体。
- **已确认**：bundle 内含完整演示手机号、姓名、企业、IP、合同、财务、隐私请求和审计记录；即使当前是虚构数据，这种把业务明细打进公共静态文件的模式不能进入生产。
- **推断**：仅沿用若依菜单 RBAC 仍不足以覆盖“园区/楼宇/企业/部门/个人/工单责任人”的行级数据边界。
- **建议**：先定义主体模型（平台员工、物业员工、企业管理员、企业成员、访客、服务商）与作用域；若依在 Controller/Service/SQL 层同时执行业务权限和数据权限，前端权限只负责体验。
- **建议**：双人复核必须使用后端当前用户身份、职责分离规则、版本锁和不可篡改审计；禁止客户端提交任意 actor 作为信任依据。
- **建议**：PRD 加入个人信息最小化、脱敏、导出水印、保留/删除、同意记录、访问审计和对象存储访问控制。

### 5. XSS、输入与文件安全

- **已确认**：管理端用模板字符串生成 HTML，并在 `web-admin/assets/index-Col4iETK.js:446` 附近整体写入 `innerHTML`；代码中存在 `x(...)` 等转义辅助函数，但模板同时接受 body/footer/action HTML 片段。
- **推断**：当前硬编码数据下未确认可利用的 XSS；一旦字段改为后端富文本、消息模板、附件名、配置链接或用户输入，转义遗漏的攻击面会显著扩大。
- **建议**：重建管理端时采用默认转义的组件渲染；富文本走白名单清洗，URL 限制协议与域名，CSP 禁止不必要的 inline/eval，服务端也做长度/格式/枚举校验。
- **已确认**：原型出现营业执照、合同、施工图纸、投诉照片、音频、转账凭证和导出文件，但没有真实上传/下载生命周期和对象存储边界。
- **建议**：定义文件类型嗅探、大小/数量、病毒扫描、私有桶、短时签名 URL、上传完成确认、业务绑定、删除/保留、预览转换和审计，不能只校验扩展名。

### 6. 性能与终端适配

- **已确认**：`mini-program/assets/` 加 `web-admin/assets/` 共约 11.14 MB；多张业务 PNG 单张超过 1 MB。
- **已确认**：两端都是单主 bundle，未看到业务级代码拆分；管理端还把大量演示数据一起打包。
- **已确认**：Windows 原型服务 `tools/serve.ps1` 对所有响应设置 `Cache-Control: no-store`。
- **推断**：直接照搬到微信小程序会遇到主包/分包、首屏、图片解码、弱网和内存压力；直接照搬管理端会导致初始 JS 和数据下载过大。
- **建议**：小程序按业务域分包，图片转 WebP/AVIF 并生成缩略图；管理端路由懒加载、表格服务端分页、字典缓存，生产静态资源使用内容哈希和长期缓存。
- **建议**：建立首屏、交互、API P95、包体和图片预算，并用真机/弱网验收，而不是只在桌面浏览器设备壳中验收。

### 7. 本地服务与运维风险

- **已确认**：`tools/serve.ps1` 只绑定 localhost，适合离线演示，不含 TLS、压缩、限流、日志、健康检查或安全响应头。
- **已确认**：请求文件不存在时，`tools/serve.ps1` 回退到 `index.html` 且保持成功状态；缺失 JS/图片也可能返回 HTML/200，削弱错误探测并产生 MIME 混淆式故障。
- **已确认**：路径约束用字符串 `StartsWith($siteRoot)`，没有显式目录分隔符边界；虽然当前仅本机演示，仍不应复用为生产静态服务器。
- **已确认**：`tools/stop.ps1` 读取 PID 文件后直接 `Stop-Process -Force`，不核验该 PID 是否仍是本项目服务；陈旧或被修改的 PID 文件可能终止无关进程。
- **已确认**：仓库没有 `.gitignore`，运行生成的 `tools/mini.pid`、`tools/web.pid` 当前已成为未跟踪文件。
- **建议**：生产使用受支持的网关/静态托管与若依部署链路；PID 文件加入忽略，本地停止脚本核验进程命令行和启动时间。

## 从纯前端原型迁移到若依的主要风险

### 领域拆分风险

- **已确认**：原型同时覆盖物业工单/投诉、设备、巡检、租赁、合同、账单、押金、电费、发票、访客、门禁、停车、空间预约、活动、内容、消息、AI 管家、隐私请求、数据治理和系统管理。
- **推断**：若一次性按页面建表、为每张页面表写 CRUD，会形成跨域耦合、重复企业/人员主档、状态枚举冲突和难以维护的万能表。
- **建议**：先确立共享主数据（园区、楼宇、空间、企业租户、人员、账号、合同主体）和业务域边界，再按“事实/状态/命令/事件/附件/审计”设计，不按页面截图直接建模。

### 若依底座适配风险

- **推断**：若依版本和形态尚未指定；RuoYi-Vue、RuoYi-Vue-Plus、Cloud 等在 Java/Spring、前端栈、租户、权限和部署复杂度上不同，过早编码会锁死架构。
- **建议**：PRD/技术方案先冻结底座版本、JDK/Spring Boot、数据库、缓存、对象存储、消息队列、部署形态和多租户策略；确认哪些使用若依原生能力、哪些是独立业务模块。
- **建议**：不要让小程序直接复用管理端 DTO；为小程序建立面向当前企业/当前用户的 BFF/API 视图，避免暴露后台字段与数据权限条件。
- **建议**：后台菜单权限、API 权限、数据范围、业务状态权限分别建模；“能看到按钮”不等于“能执行动作”。

### 外部系统与异步一致性风险

- **已确认**：原型文案暗示微信、短信/站内消息、支付、门禁、停车、财务、发票、对象存储、AI 和数据同步，但仓库没有任何真实连接器或回调协议。
- **推断**：这些系统会引入签名、重放、回调乱序、重复通知、部分失败、对账和人工补偿，不能用前端 toast 语义替代。
- **建议**：每个外部集成建立适配器、外部 ID 映射、幂等键、请求/回调日志、重试/死信、对账任务和人工补偿台；上传成功、受理成功与业务完成必须分状态。

## 建议的生产化门禁

1. 找回或重建可维护源码，构建可重复，依赖与许可证清单可审计。
2. 形成页面/动作清单并完成 PRD 逐项定级：展示、查询、命令、审批、异步任务、外部集成。
3. 先审定领域模型、状态机、权限矩阵、租户边界、金额与时间规则，再冻结 OpenAPI 契约。
4. 若依完成服务端认证、权限、数据隔离、事务、幂等、审计和附件安全；前端不承担信任边界。
5. 小程序通过微信开发者工具和真机验证登录、授权、订阅、上传、支付/退款（如纳入范围）及隐私合规。
6. 建立单元、领域状态机、API 契约、权限越权、并发、E2E、可访问性、性能和安全测试。
7. 建立开发/测试/预发/生产配置、迁移、备份恢复、日志指标追踪、告警、灰度与回滚方案。
8. 用真实失败场景验收：重复提交、回调重复/乱序、余额不足、审批并发、文件扫描失败、消息失败、外部系统超时和数据对账差异。

## 不应直接继承的实现

- 不直接修改或二次开发两个压缩 bundle。
- 不把客户端角色切换、actor 选择和路由判断当作权限实现。
- 不把 `Date.now()`/最大 ID 加一当作业务主键策略。
- 不把固定演示日期、演示金额和种子状态当作正式规则。
- 不把成功 toast 当作提交、落库、支付、上传、导出或消息送达证据。
- 不把 `tools/serve.ps1`/`tools/stop.ps1` 当作生产服务或进程管理方案。
