# OPCSpace 一体化产品工程设计

**状态：** 已批准设计

**日期：** 2026-08-28

**目标：** 将现有管理端与小程序双端原型重建为一个统一产品：保留本地 PRD 演示环境，以若依体系建设正式管理端和后端，以 RuoYi-App 建设微信小程序，并实现账号、权限、数据和业务状态的端到端贯通。

## 1. 已确认的产品决策

1. 首版只服务和盛大厦，但核心业务表携带 `project_id`，为同一物业下未来多园区扩展保留边界。
2. 当前 `mini-program/` 和 `web-admin/` 仅作为产品原型和验收证据，不作为正式源码继续开发。
3. PRD 静态演示环境只保留在本地根仓，不部署到云端，也不连接正式 API。
4. 正式管理端采用若依规范主导的混合模式：标准台账直接生成，领域对象生成后增强，复杂运营页面按原型定制。
5. 管理端前端属于若依体系，但与 Java 后端物理分离、独立构建和发布。
6. 正式小程序以 RuoYi-App Vue 3 分支为底座，发布到微信小程序平台。
7. 正式后端以 RuoYi-Vue Spring Boot 3 分支为底座，首期采用模块化单体。
8. 小程序账号由管理端预建；物业创建企业管理员，企业管理员创建、邀请和停用本企业成员。
9. 首条双端业务闭环选择报修工单：小程序提交、后台派单处理、用户验收评价。
10. 首发部署采用云服务器加托管 MySQL、Redis、对象存储；Docker Compose 仅用于本地开发和联调。

## 2. 产品与代码边界

### 2.1 目标目录

```text
opcspace/
|-- index.html                         # 本地 PRD 演示入口
|-- prd-demo/
|   |-- admin/                         # 冻结管理端原型
|   `-- mini/                          # 冻结小程序手机壳原型
|-- apps/
|   |-- admin-web/                     # 若依 Vue3 + TypeScript 管理端
|   `-- mini-app/                      # 小程序产品源码
|-- services/
|   `-- backend/                       # 后端产品源码
|-- contracts/
|   |-- openapi/                       # 管理端与小程序 API 契约
|   `-- vocabulary/                    # 状态、错误码、权限码和事件名称
|-- database/
|   |-- migrations/                    # 版本化数据库迁移
|   `-- seeds/                         # 非敏感基准字典与开发数据
|-- deploy/
|   |-- compose/                       # 本地开发基础设施
|   |-- environments/                  # 环境配置样例，不含 Secret
|   `-- release/                       # 发布、回滚和制品清单
|-- scripts/                           # 基线、构建、测试和发布入口
|-- docs/                              # PRD、架构、追踪矩阵和运行手册
`-- workspace-baseline.json
```

### 2.2 根仓职责

根仓是产品工程，负责：

- 直接追踪管理端、小程序和后端的产品源码。
- 保存 PRD、原型证据、OpenAPI、数据库迁移和部署定义。
- 定义产品版本与发布清单。
- 提供跨组件构建、测试、契约校验和发布入口。

根仓不把管理端、小程序和后端合并成一个构建。三者必须能独立构建、部署和回滚。

### 2.3 上游来源与产品远端

OPCSpace 使用单一产品远端。若依底座以合规源码快照导入根仓，不保存为 Git 子模块，也不公开其上游提交历史。适用的 MIT 许可证、版权与初始快照记录必须保留；后续上游同步以独立源码导入提交完成，不与业务功能混合。

## 3. 管理端设计

### 3.1 若依体系的组成

`apps/admin-web/` 是若依 Vue 3 + TypeScript 管理端；`services/backend/` 是 RuoYi-Vue Java 后端。二者属于同一若依体系，但物理分离：

- 管理端复用登录、动态菜单、权限指令、字典、通用组件和请求封装。
- 后端提供用户、部门、角色、菜单、数据权限、日志、代码生成和业务 API。
- 前端静态制品与后端容器分别发布，允许独立回滚。

### 3.2 代码生成三级策略

| 等级 | 页面类型 | 实施方式 | 示例 |
|---|---|---|---|
| Level 1 | 标准台账 | 直接使用 Vue3 TypeScript 生成模板，经检查后进入管理端 | 园区、楼宇、服务类型、通知模板、业务字典 |
| Level 2 | 领域对象 | 生成 Java、Mapper、API 和页面骨架，再增加状态机、数据范围、校验和领域服务 | 企业、空间、资产、合同、账单、活动 |
| Level 3 | 复杂编排 | 沿用若依登录、权限、API、字典和组件规范，页面按原型定制 | 运营看板、工单详情、预约日历、审批中心、财务对账 |

生成代码的生命周期：

1. 先评审领域模型和数据库迁移。
2. 在代码生成器中选择 Vue 3 TypeScript 模板。
3. 生成 Java、Mapper、TypeScript API、类型、Vue 页面和菜单 SQL。
4. 在临时生成目录进行差异审查。
5. 通过审查后放入对应业务模块和管理端模块。
6. 已人工增强的文件禁止被后续生成操作直接覆盖。

### 3.3 部门与业务组织

- `sys_dept` 表达物业内部组织，例如客服、工程、财务、招商和内容运营。
- 企业租户使用独立的 `company` 和 `company_member` 模型，不进入物业部门树。
- 园区使用独立的 `project` 模型，不用部门节点代替园区。
- 若依角色和菜单权限决定后台操作能力；项目、企业、空间和工单范围由业务数据权限补充。

## 4. 小程序设计

### 4.1 正式工程

`apps/mini-app/` 从 RuoYi-App `vue3` 分支建立产品分支，使用 Vue 3、Pinia 和 uni-app。现有手机壳原型只用于还原页面结构、字段和视觉验收。

正式工程必须具备命令行可重复构建入口，以支持测试、体验版和正式版流水线；不能只依赖开发者本机 HBuilderX 手工发布。

### 4.2 受控账号绑定

1. 物业员工在管理端创建企业档案和首位企业管理员。
2. 企业管理员在小程序创建或邀请本企业成员。
3. 成员账号保存已验证手机号、企业关系、角色和状态。
4. 用户首次进入小程序时调用微信登录，后端换取微信身份。
5. 用户输入预建手机号和企业管理员签发的一次性激活码；激活码经哈希保存、24 小时过期且成功使用后立即失效。
6. 后端写入 `wechat_identity` 与 `app_user` 的绑定关系。
7. 未预建、已停用或企业关系失效的账号不能进入园区业务。

企业管理员只能管理本企业成员；物业人员保留跨企业查询、审计和强制停用能力。

访客不创建完整小程序账号，只使用受限、可撤销、可过期的访客凭证。

## 5. 身份、权限与数据隔离

### 5.1 两套身份域

| 身份域 | 核心模型 | 使用者 | 认证结果 |
|---|---|---|---|
| 管理端 | `sys_user`、`sys_dept`、`sys_role` | 物业员工和平台管理员 | Admin JWT |
| 小程序 | `app_user`、`company_member`、`wechat_identity` | 企业管理员和企业成员 | App JWT |

Admin JWT 与 App JWT 使用不同受众和权限集合。管理端不能使用 App JWT，小程序不能使用 Admin JWT。

### 5.2 权限层次

1. 菜单权限：后台能否进入页面。
2. API 权限：能否调用查询或命令。
3. 数据范围：能访问哪些项目、企业、空间和工单。
4. 状态权限：在对象当前状态下能否受理、派单、完工、验收或关闭。

首版只有和盛大厦一个项目，但业务数据显式保存 `project_id`。服务端从当前身份和成员关系计算范围，不能信任前端提交的 `project_id`、`company_id` 或操作者身份。

## 6. API 与共享业务状态

### 6.1 API 边界

- 管理端：`/api/admin/v1/**`
- 小程序：`/api/app/v1/**`
- 外部回调：`/api/callback/v1/{provider}/**`
- OpenAPI 是接口权威来源，管理端和小程序客户端均由契约生成。

两端不直接互调。管理端和小程序只通过后端共享权威业务数据与状态。

### 6.2 写操作规则

- 前端提交业务命令，不直接提交最终状态。
- 创建操作携带幂等键，避免网络重试产生重复记录。
- 更新操作携带版本号，检测并发修改。
- 服务端验证身份、数据范围、当前状态、参数和职责分离要求。
- 状态改变同时写业务记录、状态事件和审计记录。
- 通知、附件处理和外部调用区分“已受理、处理中、成功、失败”。

## 7. 首条业务纵切：报修工单

### 7.1 正常流程

1. 已绑定企业成员在小程序选择位置、问题类别并上传附件。
2. 小程序调用 `POST /api/app/v1/work-orders`，提交报修命令和幂等键。
3. 后端验证成员、企业、项目和空间范围，创建工单与审计事件。
4. 管理端客服查看待受理工单并执行受理、派单。
5. 工程人员接单、开始处理、填写处理结果并提交完工。
6. 后端产生状态事件并创建小程序通知。
7. 用户在小程序查看进度并执行验收、评价。
8. 后端关闭工单，保留完整时间线、附件、责任人和评价。

### 7.2 状态机

```text
submitted
  -> accepted
  -> assigned
  -> processing
  -> pending_acceptance
  -> completed
  -> closed
```

异常分支包括：`cancelled`、`reassigned`、`suspended`、`reopened`。每个转换必须定义执行角色、前置条件、通知、SLA 和审计内容。

### 7.3 首版异常处理

- 重复提交：幂等键返回同一工单结果。
- 附件上传失败：不创建引用未完成附件的工单，允许用户重试。
- 并发派单：版本冲突返回明确错误并刷新工单。
- 账号停用：现有 token 失效，未完成工单保留并由物业转派。
- 通知失败：不回滚工单状态，进入可重试投递任务并在后台显示失败。
- 用户长时间未验收：按配置提醒，达到期限后自动关闭并记录规则来源。

## 8. 后端模块

首个 Alpha 只启用支撑身份、主数据和报修纵切所需模块：

| 模块 | 首版职责 |
|---|---|
| `opc-foundation` | 项目、楼宇、楼层、空间、企业、成员和服务商主数据 |
| `opc-service` | 报修、工单、派单、处理记录、SLA、评价和时间线 |
| `opc-content` | 小程序公告和基础消息内容 |
| `opc-governance` | 业务审计、通知任务、字典与配置发布边界 |

资产、租赁、财务、停车、门禁和 AI 模块保留在后续版本，不进入首个 Alpha 的实现范围。

## 9. 构建、环境与部署

### 9.1 独立制品

| 组件 | 构建结果 | 部署位置 |
|---|---|---|
| `apps/admin-web` | 带内容哈希的静态资源 | 云对象存储与 CDN |
| `apps/mini-app` | 微信小程序上传制品 | 微信小程序平台 |
| `services/backend` | Java 容器镜像 | 云服务器容器运行环境 |
| `prd-demo` | 本地静态文件 | 不部署 |

### 9.2 基础设施

- 云 MySQL 保存权威业务数据。
- 云 Redis 保存会话、缓存、幂等和短期协调数据，不作为业务事实唯一存储。
- 云对象存储保存报修附件和导出文件，使用私有桶和短时授权 URL。
- 云服务器运行后端容器、反向代理、健康检查、日志和监控代理。
- 所有外部访问使用 HTTPS；微信平台配置正式请求和上传合法域名。

### 9.3 环境

| 环境 | 用途 | 数据与集成 |
|---|---|---|
| dev | 本地开发 | Docker Compose、开发数据、模拟微信身份 |
| test | 自动测试 | 独立数据库、契约测试、E2E |
| staging | 上线前验证 | 微信体验版、云沙箱、脱敏数据 |
| prod | 正式运营 | 正式微信版本和正式云资源 |

各环境的数据库、Redis、对象存储桶、域名和 Secret 完全隔离。

## 10. 版本与发布

根仓产品版本采用 SemVer。`v0.1.0-alpha.0` 发布清单必须锁定：

- `admin-web` 提交和静态制品摘要。
- `mini-app` 提交、构建摘要和微信版本号。
- `backend` 提交、容器镜像摘要。
- 数据库迁移版本。
- OpenAPI 契约版本。
- 环境配置版本，不包含 Secret 值。

根仓标签是对外产品版本。子项目可独立部署和回滚，但任何生产组合都必须对应一个根仓发布清单。

## 11. 当前目录迁移顺序

1. 将当前 `mini-program/` 移动到 `prd-demo/mini/`。
2. 将当前 `web-admin/` 移动到 `prd-demo/admin/`。
3. 保留根 `index.html` 作为本地 PRD 演示入口，并更新资源路径。
4. 将 RuoYi-App 源码快照导入 `apps/mini-app/`，后续建立 Vue 3 产品基线。
5. 将 RuoYi-Vue 源码快照导入 `services/backend/`，后续建立 Spring Boot 3 产品基线。
6. 新增 `apps/admin-web/` 若依 Vue 3 TypeScript 工程。
7. 更新 `workspace-baseline.json` 和基线校验脚本，验证无嵌套 Git 元数据。
8. 建立 `contracts/`、`database/` 和 `deploy/` 目录。
9. 验证本地演示入口、三个正式工程构建和根仓源码追踪。
10. 开始身份、主数据和报修工单纵切。

迁移期间不删除原型内容，不修改压缩 bundle，不把演示数据迁入正式数据库。

## 12. 测试与验收

### 12.1 基座验收

- 根仓普通克隆后能恢复所有正式源码组件。
- 三个正式工程可独立构建。
- PRD 演示入口仍能本地打开双端原型。
- 管理端可使用若依登录、部门、角色、菜单、字典和代码生成。
- dev、test、staging、prod 配置不包含硬编码 Secret。

### 12.2 报修纵切验收

- 未预建、已停用和跨企业用户无法提交工单。
- 企业成员只能选择授权项目和空间。
- 管理端数据范围阻止跨项目、跨职责越权。
- 重复提交不产生重复工单。
- 所有状态转换都有执行人、时间、前后状态和审计原因。
- 通知失败不会导致工单状态回滚。
- 小程序能看到与管理端一致的工单进度和时间线。
- 用户验收评价后工单正确关闭。

## 13. 非目标

首个 Alpha 不包含：

- 多物业公司 SaaS 租户平台。
- 真实支付、退款和电子发票。
- 门禁、停车、BA 和电表设备集成。
- 完整资产、合同、租赁和财务业务。
- AI 自动执行业务动作。
- PRD 静态演示网站部署。

## 14. 进入实施前的外部输入

实施开始前需要准备：

- RuoYi-Vue、RuoYi-App 与管理端的 OPCSpace 可写远端仓库地址。
- 微信小程序主体、AppID、体验成员和合法域名配置权限。
- 云账号中 dev/test/staging/prod 的资源命名和访问权限。
- 和盛大厦物业组织、首批企业、空间和试点账号的脱敏基准数据。

这些输入不会改变已批准架构；缺失时只阻塞对应远端、微信或云环境的实际联调。
