# OPCSpace 模块化单体架构

## 决策

首期后端在 `services/backend/` 中采用模块化单体：一个部署单元、一个受控数据库边界，以 Java 模块隔离领域职责。首期不采用 RuoYi-Cloud，不引入注册中心、分布式事务或跨服务调用。

这是一份目标架构说明，不表示下列业务模块或接口已经实现。

## 接入边界

```text
apps/admin-web  -> /api/admin/v1/**
apps/mini-app   -> /api/app/v1/**
external system -> /api/callback/v1/{provider}/**
                           |
                           v
                   services/backend
                           |
        +------------------+------------------+
        |                  |                  |
 opc-foundation       opc-service        opc-content
        \__________________|__________________/
                           |
                    opc-governance
```

- 管理端与小程序不直接互调，也不以浏览器状态作为业务事实。
- 外部回调必须验签、防重放、幂等，并记录外部 ID 与处理结果。
- OpenAPI 是接口权威来源；客户端和 DTO 由契约生成。

## 模块职责

| 模块 | 拥有的职责 | 不应承担 |
|---|---|---|
| `opc-foundation` | 项目、楼宇、楼层、空间、企业、成员、服务商主数据 | 工单流转和消息投递 |
| `opc-service` | 报修、工单、派单、处理、SLA、评价、时间线 | 伪造身份或绕过主数据范围 |
| `opc-content` | 公告与基础消息内容 | 通知投递状态和业务审计 |
| `opc-governance` | 业务审计、通知任务、字典与配置发布边界 | 替代各领域的业务状态机 |

模块只能通过显式应用服务和领域事件协作，禁止跨模块直接修改对方表。需要异步投递时，先在本地事务中写入事实与 Outbox，再由调度任务投递；首期不因预期吞吐提前引入 MQ。

## 身份域

管理端与小程序采用独立身份域：

| 身份域 | 核心模型 | 凭证 | API |
|---|---|---|---|
| 管理端 | `sys_user`、`sys_dept`、`sys_role` | Admin JWT | `/api/admin/v1/**` |
| 小程序 | `app_user`、`company_member`、`wechat_identity` | App JWT | `/api/app/v1/**` |

两个 token 使用不同 audience 和权限集合。管理端不能使用 App JWT，小程序不能使用 Admin JWT。服务端从当前可信身份计算 `project_id`、`company_id` 与可见数据范围，不信任客户端提交的操作者身份。

## 写操作与审计

- 前端提交业务命令，不直接提交最终状态。
- 创建操作携带幂等键，更新操作携带版本号。
- 服务端同时验证身份、API 权限、数据范围、当前状态和职责分离要求。
- 状态改变在同一事务中记录业务事实、状态事件和审计记录。
- 通知、附件和外部调用区分“已受理、处理中、成功、失败”，HTTP 200 不等于业务完成。

## 未来拆分门槛

只有当独立团队、独立发布节奏、吞吐、故障隔离或合规隔离形成可验证需求时，才从单体中拆服务。拆分前必须先稳定模块 API、数据所有权、事件和回滚语义。
