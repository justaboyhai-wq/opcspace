# 外部集成映射

## 当前真实网络边界

- 当前双端原型没有接入任何真实业务后端、第三方 SaaS、支付、短信、地图或 AI API。
- 对 JS bundle 的检索未发现业务 `fetch`、Axios、XHR、WebSocket、SSE、GraphQL 或固定 `/api/` 调用。
- bundle 内的 `fetch` 仅属于 ES module preload polyfill；不能把它视为业务联网证据。
- `README.txt` 明确声明可离线运行，所有数据不会提交到真实业务系统。
- 根 `index.html` 只链接本机 `http://localhost:18081/` 和 `http://localhost:18082/`。
- 小程序端引用的字体、设备壳、状态栏和业务图片全部来自 `mini-program/assets/` 本地文件。
- 管理端中的缩略图有内联 `data:image/svg+xml`，没有远程媒体源。
- 构建产物中的 React 官方错误说明 URL 与 W3C 命名空间是框架常量，不是产品外部集成。

## 当前鉴权与权限状态

- 未发现登录 API、OAuth、JWT、Bearer Header、Cookie Session、验证码服务或 token 持久化。
- 管理端在 `web-admin/assets/index-Col4iETK.js` 中内置用户、部门、角色、权限和数据范围演示数据。
- 原型角色包含超级管理员、物业运营、工程管理、财务管理、招商管理、内容运营等。
- 页面访问与操作按钮通过前端 role/permission 判断模拟；刷新后恢复，且可被浏览器端修改。
- 小程序端含手机号、微信、权限等交互文案，但未发现微信登录 SDK 或真实授权调用。
- 生产方案必须由 RuoYi 后端负责身份认证、RBAC、数据权限、账号状态、审计和会话失效。

## 当前存储状态

- 没有数据库连接、对象存储 SDK、缓存客户端或文件上传接口。
- 没有 `localStorage`、`sessionStorage`、IndexedDB 或业务 Cookie 持久化。
- 管理端演示集合直接编译进 `web-admin/assets/index-Col4iETK.js`，大量使用 `Object.freeze`。
- 小程序端演示数据和导航状态直接编译进 `mini-program/assets/index-MfHB7Usc.js`。
- 本地图片和字体由静态服务读取；`tools/serve.ps1` 不提供上传、写入或目录 API。
- `tools/*.pid` 只存静态服务器进程号，与业务数据无关。

## 建议的 RuoYi 集成边界

- API 网关：统一 `/api/v1`（具体前缀待定）、错误码、请求 ID、幂等键和分页格式。
- 身份：管理端复用 RuoYi 登录/RBAC/数据权限；小程序端建立微信身份与园区成员/企业账号绑定关系。
- 文件：合同、发票、报修图片、活动素材等应进入对象存储，数据库只保存元数据和受控 URL。
- 消息：业务事件进入消息中心，再由微信、短信、邮件、站内信适配器投递并记录回执。
- 支付：支付订单、业务账单、渠道流水和退款单分离，所有回调必须验签、幂等和可重放审计。
- IoT：门禁和 BA/设备集成应通过独立适配层或边缘网关，避免厂商协议侵入核心业务模块。
- AI：AI 只能生成建议或业务草稿；支付、退款、开门、发票等高风险动作必须走明确授权和后端校验。
- 审计：角色变更、匿名报修解密、导出、财务复核、设备控制和 AI 人工接管均需不可抵赖日志。

## 配置与 Secret 约束

- 当前仓库没有可沿用的外部服务配置变量，也没有发现任何真实凭据。
- 生产化时仅在配置中心或 Secret 管理系统中保存敏感值，前端不得打包密钥。
- 建议按能力定义变量名而非绑定供应商，例如 `WECHAT_APP_ID`、`SMS_PROVIDER`、`PAYMENT_CALLBACK_BASE_URL`、`OBJECT_STORAGE_BUCKET`、`AI_PROVIDER`。
- 私钥、证书、数据库口令、短信密钥、支付 API 密钥和模型密钥不得写入 Git、日志或前端运行时配置。
- 每个外部回调都需独立的验签配置、允许时钟偏差、重放保护、回调日志和告警。

## 关键未知项与 PRD 访谈题

- 微信小程序是否必须原生开发，还是允许 uni-app/Taro；当前仓库无法回答。
- 用户体系是个人、企业成员、企业管理员与物业员工共用身份域，还是多套账号体系。
- 是否多园区、多楼宇、多物业公司运营，以及 RuoYi `dept_id` 能否表达真实数据边界。
- 财务模块是否产生真实支付与税务凭证，还是只同步第三方物业/财务系统。
- 门禁、BA、停车、电表和会议室硬件的现有厂商、协议及现场网络条件未知。
- 短信、邮件、微信订阅消息的供应商、发送规模、SLA 和合规要求未知。
- AI 管家的知识来源、可执行动作范围、人工接管机制、留痕和内容合规标准未知。
- 文件保存年限、个人信息脱敏、匿名投诉解密权限与隐私授权规则未知。
- 是否需要与 ERP、财务、CRM、电子合同、工单或统一身份平台双向同步未知。
- 生产回调域名、网络隔离、等保等级、容灾目标和监控平台未知。

## 实施前置验证

- 逐个页面把模拟动作归类为纯查询、内部写操作、外部指令和高风险审批。
- 为每个外部系统确认系统所有者、沙箱、协议文档、限流、幂等、回调和故障降级。
- 先冻结领域实体与状态机，再定义 OpenAPI；不要直接从压缩 bundle 反推数据库表结构。
- 建立最小纵切验证：小程序登录/成员绑定、报修上传、后台派单、状态通知、用户验收。
- 支付、开票、门禁和 AI 动作应各自做独立技术 Spike 与安全评审后再进入主计划。
