## 2. 为什么只保留这四类正文

一个可执行 PRD 需要回答四件不同的事：

1. **做什么和不做什么**：由主 PRD 负责。
2. **前后端功能怎样对应**：由功能追溯附件负责。
3. **业务怎样从触发走到关闭**：由闭环设计附件负责。
4. **哪些规则还不能确定**：由决策清单负责。

原型逐页盘点、按钮映射和历史流程稿是形成上述结论的证据，不应继续与当前需求并列，否则会造成版本和权威性冲突。

## 3. 权威与冲突处理

1. 产品范围、角色和排除项以 `OPCSpace-PRD.md` 为准。
2. 页面、入口和编号事实以 `OPCSpace-FUNCTION-TRACEABILITY.md` 为准。
3. 已评审的业务规则写入 `OPCSpace-CLOSED-LOOP-DESIGN.md`；仍在 `OPCSpace-DECISIONS.md` 中开放的问题不得写成确定规则。
4. 归档文件与当前文件冲突时，归档文件不覆盖当前文件。
5. 原型存在页面或交互不等于正式代码已经实现。

## 4. 当前统一范围

- 管理端责任族为招商、财务、运营、内容、超级管理员；统一待办、审批、客服、消息、审计和配置是跨角色共用能力。
- 普通报修属于运营服务，不连接设备台账、巡检或维保告警。
- 设备台账、物业巡检、维保、设备告警、施工巡检、BA/传感器/设备实时监控不进入当前产品。
- 访客二维码、门禁授权、闸机事件、核销、设备离线和人工放行明确保留。
- 停车只保留车辆、月租、优惠、账单、缴费和记录；不设计停车硬件控制。
- 电费只保留账户、账单、充值、回单和入账；不设计电表管理或实时抄表。

## 5. 维护规则

1. 当前文件名不带版本号，避免每次修订复制出新文件。
2. 内容版本写在文档头部修订历史中，正式基线通过 Git 标签或发布记录冻结。
3. 范围变更先改主 PRD，再同步追溯、闭环设计和决策清单。
4. `MP-*`、`FC-*` 和管理端稳定编号只增不复用；被排除的历史编号留在归档证据中。
5. 每条闭环必须同时说明正常路径、异常路径、权限负向、反馈、审计和端到端验收。
